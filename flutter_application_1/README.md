# Valorant Explorer

Flutter-приложение для просмотра истории матчей VALORANT, поиска и фильтрации матчей, а также для личных заметок к ним.
Это вариант задания «Post Explorer»: вместо JSONPlaceholder используются два источника данных.

| Источник | Что даёт | Где |
|---|---|---|
| [HenrikDev VALORANT API](https://docs.henrikdev.xyz) | матчи игрока, детали матча, аккаунт, справочник агентов (только GET) | `https://api.henrikdev.xyz`, нужен ключ |
| Свой REST-сервер заметок | заметки к матчам: GET + **POST** | `json-server` в Docker, папка [server/](server/) |

У VALORANT-API нет запросов на создание данных, поэтому POST идёт на свой сервер в Docker.

## Соответствие требованиям задания

| № | Требование | Запрос в приложении (Retrofit) |
|---|---|---|
| 1 | `GET /posts?_page&_limit`: список с пагинацией | `GET /valorant/v1/stored-matches/{region}/{name}/{tag}?page=&size=` |
| 2 | `GET /posts/{id}`: детали | `GET /valorant/v4/match/{region}/{matchId}` |
| 3 | `GET /posts?userId=`: фильтрация | тот же stored-matches с `?map=` / `?mode=` (серверный фильтр) |
| 4 | `GET /posts/{id}/comments` | `GET /notes?matchId=` (заметки к матчу) |
| 5 | `POST /posts` с валидацией | `POST /notes` |
| доп. | `GET /users/{id}` | `GET /valorant/v2/account/{name}/{tag}` (профиль игрока) |
| доп. | `GET /users`: список для выбора в форме | `GET /valorant/v1/content` (список агентов) |

Retrofit-интерфейсы описаны в [henrik_api.dart](lib/data/remote/henrik_api.dart) и [notes_api.dart](lib/data/remote/notes_api.dart).

## Запуск

Нужны Flutter 3.47+ (Dart 3.13), Docker Desktop и ключ HenrikDev (выдаётся в их Discord, вида `HDEV-...`).

```bash
# 1. Сервер заметок (http://localhost:3000)
cd server
docker compose up -d --build
cd ..

# 2. Ключ и игрок по умолчанию: заполнить env.json (файл в .gitignore)
cp env.example.json env.json

# 3. Зависимости и генерация кода (json_serializable, retrofit_generator)
flutter pub get
dart run build_runner build

# 4. Запуск
flutter run --dart-define-from-file=env.json

# 5. Тесты
flutter test
```

`env.json`:

```json
{
  "HENRIK_API_KEY": "HDEV-...",
  "PLAYER_REGION": "eu",
  "PLAYER_NAME": "YourName",
  "PLAYER_TAG": "1234",
  "NOTES_BASE_URL": ""
}
```

* Игрока можно сменить в приложении (иконка в AppBar). Выбор сохраняется в Hive.
* Если `NOTES_BASE_URL` пустой, адрес выбирается автоматически: в эмуляторе Android это `http://10.0.2.2:3000`, на остальных платформах `http://localhost:3000`. Для реального телефона укажите IP компьютера, например `http://192.168.1.10:3000`.
* Ключ передаётся только заголовком `Authorization` и только на хост HenrikDev. В git и в логи он не попадает: `LogInterceptor` не печатает заголовки.

### Задача каждого слоя

* **Dio** — HTTP-клиент. Один экземпляр на всё приложение, в нём общие таймауты, базовый URL и interceptors (логирование, заголовки, retry). Ошибки приходят как `DioException` с типом: таймаут, нет сети, плохой ответ.
* **Retrofit** — декларативное описание API аннотациями (`@GET`, `@Path`, `@Query`, `@Body`). Генератор пишет код запросов, поэтому URL и параметры не собираются вручную и типы проверяются при компиляции.
* **json_serializable** — генерирует `fromJson` и `toJson`. Ручного парсинга нет. `checked: true` превращает отсутствующее обязательное поле в `CheckedFromJsonException`, а `ErrorMapper` переводит его в `ParsingException`, так что приложение не падает. Неизвестные поля огромного ответа v4 просто игнорируются.
* **Repository** — единая точка доступа к данным. Решает, когда брать кэш, а когда сеть, обновляет кэш после успешного ответа и переводит любые исключения в `AppException`. UI и Cubit ничего не знают про Dio, Hive и JSON, поэтому их легко тестировать с фейковым репозиторием.

## Кэширование (Hive)

`AppCache` хранит JSON-строки в `Box<String>` вместе с временем сохранения. TypeAdapter-ы не нужны: используются те же `toJson` и `fromJson`. Повреждённая запись удаляется и считается отсутствующей.

Ключи кэша: матчи `matches:{игрок}:{фильтр}` (у каждого фильтра свой список), детали `match:{id}`, заметки `notes:{matchId}` и `notes-local:{matchId}`, а также профиль, список агентов и выбранный игрок.

Стратегия «сначала кэш, потом сеть»:

1. Если в кэше есть данные, они показываются сразу, сверху плашка «Сохранённые данные от … Обновляем…».
2. Параллельно уходит запрос на сервер.
3. При успехе данные и кэш обновляются, плашка исчезает.
4. При ошибке данные остаются на экране, плашка меняется на «Сохранённые данные от … Нет подключения…», ниже snackbar с причиной. Последний успешный результат не удаляется.
5. Pull-to-refresh работает на всех экранах: и в списке, и в деталях.

### Поведение в разных сценариях

* **Первый запуск.** Кэш пуст, поэтому виден полноэкранный индикатор загрузки (Loading). После ответа сервера список отображается (Success), первая страница сохраняется в Hive. Если сети нет, показывается Error с понятным текстом и кнопкой «Повторить».
* **Повторное открытие.** Сразу видны сохранённые матчи (Cached) с плашкой и маленьким индикатором. Затем первая страница заменяется свежими данными. Каждая загруженная страница дописывается в кэш без дубликатов, поэтому после перезапуска доступно всё, что было пролистано.
* **Нет интернета.** Видны сохранённые матчи, детали ранее открытых матчей и их заметки. Плашка сообщает, что данные из кэша и сервер недоступен. Если для экрана кэша нет, показывается Error и кнопка повтора. Приложение не падает.

## Пагинация, фильтрация, поиск

* Первая загрузка — 10 матчей (`page=1&size=10`). Следующая страница подгружается за 300 px до конца списка, внизу показывается индикатор.
* Защита от дублей: пока `pageStatus == loading`, новые вызовы игнорируются (`emit` синхронный). Кроме того, при склейке страниц совпадающие `matchId` отбрасываются.
* Ошибка следующей страницы показывается внизу списка с кнопкой «Повторить», загруженный список при этом сохраняется.
* Серверные фильтры **по карте** и **по режиму** сбрасывают страницы. Устаревший запрос отменяется через `CancelToken`, а его ответ отбрасывается по номеру поколения, поэтому старые результаты не смешиваются с новыми.
* **Поиск** по карте, агенту и режиму работает локально, только по загруженным матчам. Это прямо написано в подсказке поля: «Поиск среди загруженных матчей (N), не по всей истории».
* **Сортировка** по дате матча: сначала новые или сначала старые.
* Есть кнопка «Сбросить», которая сбрасывает все фильтры, поиск и сортировку.

## Создание заметки (POST)

Экран [create_note_screen.dart](lib/presentation/screens/create_note_screen.dart):

* `title` обязателен, 5–100 символов; `body` обязателен, 10–1000 символов; агент выбирается из списка `GET /valorant/v1/content` (аналог `userId` из списка пользователей).
* Валидация проходит до отправки: в форме и повторно в `CreateNoteCubit.submit`. Правила вынесены в `NoteValidator`.
* Пока идёт запрос, кнопка заблокирована и показывает индикатор, поля отключены, повторный `submit` игнорируется.
* После успеха показывается объект, который вернул сервер (JSON). Заметка добавляется в список с пометкой **«создано локально»**: объект взят из ответа POST, а не из списочного запроса. Когда следующий `GET /notes` вернёт эту заметку, пометка исчезает.
* При ошибке появляется snackbar с понятным текстом, введённые данные сохраняются.

> В отличие от JSONPlaceholder, наш json-server действительно сохраняет POST в `db.json`. При перезапуске контейнера база сбрасывается к исходным данным.

## Состояния интерфейса

`ViewStatus`: `loading`, `success`, `cached`, `empty`, `error`. Отдельно от него:

* `PageStatus` (`idle`, `loading`, `error`) — подгрузка следующей страницы;
* `isRefreshing` — pull-to-refresh или фоновое обновление поверх кэша;
* `SubmitStatus` (`idle`, `submitting`, `success`, `failure`) — отправка формы;
* в деталях матч и заметки грузятся двумя независимыми `Resource<T>`.

Единого флага `isLoading` нет.

## Обработка ошибок

`ErrorMapper.map` — единая точка, через которую репозитории пропускают любые исключения.

| Ситуация | Класс | Сообщение пользователю |
|---|---|---|
| нет соединения | `NoConnectionException` | Нет подключения к интернету или сервер недоступен |
| таймаут | `TimeoutException` | Сервер слишком долго не отвечает |
| HTTP 4xx | `ClientException(code)` | 401/403 → проверьте ключ, 404 → не найдено, 429 → лимит API |
| HTTP 5xx | `ServerException(code)` | На сервере произошла ошибка |
| некорректный JSON / нет поля | `ParsingException` | Данные в неожиданном формате |
| прочее | `UnknownException` | Что-то пошло не так |

Технические подробности (метод, URL без query, тип ошибки, код) пишутся в `dart:developer log` с именем `ValorantExplorer.error`. В интерфейсе показывается только `userMessage`.

**Как продемонстрировать ошибки** (middleware в [server/middleware.js](server/middleware.js)):

```bash
curl "http://localhost:3000/__chaos/on?status=500"   # все запросы к серверу заметок → 500
curl "http://localhost:3000/__chaos/off"             # вернуть нормальную работу
docker compose -f server/docker-compose.yml stop     # сервер заметок недоступен
```

Для HenrikDev достаточно включить авиарежим или указать неверный ключ (401) или несуществующий Riot ID (404).

## Дополнительное задание

* **Retry policy** ([retry_interceptor.dart](lib/core/network/retry_interceptor.dart)): повторяются только GET-запросы при таймауте, обрыве соединения и ответах 502/503/504, не больше 2 раз с задержкой 0,5 с и 1 с. POST никогда не повторяется автоматически, чтобы не создать дубликат заметки; это проверяет тест.
* **Отмена запросов**: при смене фильтра или игрока предыдущий запрос списка отменяется через `CancelToken`.
* **Элементы Clean Architecture**: репозитории описаны интерфейсами (`abstract interface class`), Cubit-ы зависят только от них.

## Ограничения

* `stored-matches` возвращает только матчи, которые HenrikDev уже сохранил для этого игрока. Если игрок давно не играл, список может быть пустым (состояние Empty).
* У базового ключа HenrikDev есть лимит запросов. При превышении приходит 429 и показывается сообщение «Слишком много запросов». Кэш помогает не упираться в лимит.
* Список карт для фильтра задан константой (`MatchFilter.maps`), потому что справочник `content` содержит и служебные карты.
